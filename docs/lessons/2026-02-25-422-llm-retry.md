2026-02-25 — 422 symbol-not-found LLM retry

Problem
Databento returns HTTP 422 when an option symbol doesn't exist (e.g. TSLA 250912P00342000).
This crashed the backtest with a fatal error. Root cause: Hariseldon fat-fingered "$342/5"
meaning "$342.5", so the parser extracted strike 342 which has no listed option.

Decision
When a quote fetch fails with 422, re-run the orchestrator via the LLM path with the failure
injected as context. The LLM re-reads the original message, identifies the typo, and returns
corrected strikes. One retry, then give up.

Key design choices
- QuoteResolutionError (src/lib/errors.ts) is thrown by market-data.ts on 422 instead of
  wrapping in a plain Error. This lets executeResolvedSignals use instanceof rather than
  string matching on error messages.
- resolveRetry callback on ResolvedPipelineOpts: executeResolvedSignals owns the retry loop.
  process-task.ts just wires the callback — it doesn't inspect results or re-orchestrate.
- failureContext on OrchestratorContext: presence forces the LLM path in the orchestrator
  (bypasses deterministic re-parse which would reproduce the same bad strike).
- No new LLM node — reuses the existing resolveLLMPath with failure context injected into
  buildNLUPrompt. The prompt explains what failed and asks the LLM to re-examine the message.
- Loop guard: retry signals are executed with optsNoRetry (no resolveRetry), so a second 422
  surfaces as a plain failed result, not another retry.

Key files
- src/lib/errors.ts — QuoteResolutionError (and future typed pipeline errors)
- src/backtest/market-data.ts — throws QuoteResolutionError on 422 in ensureRange()
- src/pipeline/execute-resolved.ts — catches QuoteResolutionError, calls resolveRetry
- src/intents/orchestrator/types.ts — failureContext field on OrchestratorContext
- src/intents/orchestrator/index.ts — forces LLM path when failureContext present
- src/intents/orchestrator/llm-path.ts — injects failure context into buildNLUPrompt
- src/pipeline/process-task.ts — wires resolveRetry callback

Watch out
- The linter added a try/catch around the retry execution in executeResolvedSignals so a
  second 422 (or any error) on the corrected signal surfaces as an executed:false result
  rather than a fatal throw. This is the right behavior.
- market-data.ts wraps DatabentoClientError for all other 4xx as a plain Error — only 422
  gets the typed QuoteResolutionError. Other 4xx errors still propagate as unhandled.
- The message log now prints the clean_text after every orchestrator decision (SKIP/EXECUTE/
  MANUAL_REVIEW) — added to logResult() in orchestrator/index.ts in the same session.
